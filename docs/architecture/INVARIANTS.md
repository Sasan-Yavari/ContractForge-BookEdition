# Invariant Register

> **Responsibility:** concise cross-cutting rules that must remain true, with implementation and test evidence pointers. Detailed architecture, data and flow specifications belong in their dedicated documents.

These cross-cutting properties must remain true across API, application, persistence, asynchronous processing, and frontend changes. Linked code, migrations, and tests are the evidence.

## Change impact and reconciliation

For every change, identify affected invariants and inspect their implementation, tests, migrations, API contract, async behavior, and documentation. For changes touching domain, persistence, transport, workers, or protocols, audit for repeated raw values that represent the same closed vocabulary and ask whether each new value has an authoritative typed representation or constant. A changed invariant is an architecture decision and requires a decision-register update or approved follow-up issue. At milestone/release review, compare this register with actual code, migrations, constraints, queues/workers, tests, issues, and roadmap; report stale evidence as follow-up work rather than implementing unrelated features. The AI-off check is a human review that derives impacted invariants from the diff and verifies each pointer directly without relying on generated summaries.
